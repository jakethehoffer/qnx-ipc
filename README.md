# qnx-ipc

Safe Rust for QNX 8.0 native message passing, pulses and resource managers.

Three crates: `qnx-ipc` (channels, typed messages, pulses, pulse timers, named
channels), `qnx-resmgr` (implement a trait, get a `/dev` path that `cat` and C
programs can use) and `qnx-ipc-sys` (bindings generated from the QNX SDP 8.0
headers at build time). A vehicle-signals demo shows QNX priority inheritance,
signals served as files, and a pulse-driven watchdog, with Rust and C programs
talking over the same native messages. Built for the QNX Global Hackathon 2026.

## Why it matters

QNX's core strength is synchronous message passing: a client sends a message,
the kernel copies it to the server and blocks the client until the server
replies. Services are built as resource managers, processes that answer the
same messages `open`, `read` and `write` use, so a driver or a vehicle service
looks like a file to every program on the system. On top of that, the kernel
runs the server's thread at the priority of the client it is serving. A
safety-critical request is handled at safety-critical priority, and a
low-priority client's request is handled at low priority, so it cannot hold off
more important work elsewhere in the system. That is what a
real-time system needs: the priority of the work follows the request through
every process it touches, without the server having to manage it.

Rust is spreading in automotive and industrial software, the markets QNX
serves, because it rules out whole classes of memory bugs. QNX is bringing Rust
to QNX 8.0 now: its Software Center ships a Rust compiler with the standard
library prebuilt for QNX (this project uses it), and its `qnx-ports` project
is porting crates such as `libc`, `mio`, `nix` and `rustix`. But when we
checked crates.io and GitHub on 2026-11-10 there was no Rust library for QNX's
native message passing or resource managers. Rust code on QNX had two choices:
avoid QNX's core strengths, or hand-write `unsafe` FFI against the raw C API,
where one missed reply leaves a client blocked forever.

`qnx-ipc` gives Rust programs that API safely. Kernel objects are owned and
released on drop; a request is answered at most once, cannot outlive its
channel, and still answers its client when it is dropped or its handler panics
(the limits are listed under
[Known limits](docs/architecture.md#known-limits)); message layouts are plain
data that C code shares. The safety argument is written out in
[docs/architecture.md](docs/architecture.md), every `unsafe` block included.

## 30-second example

A resource manager in safe Rust. After this runs, `cat /dev/hello` on the QNX
target prints `hello from Rust`:

<!-- begin: crates/qnx-resmgr/examples/hello_device.rs (checked by tools/test-all.sh) -->
```rust
//! Serves `/dev/hello` until killed: `cat /dev/hello` prints `hello from Rust`.
//!
//! Run as root (attaching under `/dev` needs it).

use qnx_resmgr::{Device, ResourceManager};

struct Hello;

impl Device for Hello {
    fn read(&self) -> qnx_ipc::Result<Vec<u8>> {
        Ok(b"hello from Rust\n".to_vec())
    }
}

fn main() -> qnx_ipc::Result<()> {
    eprintln!("serving /dev/hello");
    ResourceManager::new("/dev/hello")?.run(Hello)
}
```
<!-- end -->

This is [`crates/qnx-resmgr/examples/hello_device.rs`](crates/qnx-resmgr/examples/hello_device.rs)
as it is; `tools/test-all.sh` fails if the two differ. `Device` also has
`write` and `devctl`, each open file reads its own snapshot of the content,
and a panicking device gives its client `EIO` while the manager keeps serving.

Message passing looks like this
([`crates/qnx-ipc/examples/ping_pong.rs`](crates/qnx-ipc/examples/ping_pong.rs)):

```rust
#[repr(C)]
#[derive(Debug, Clone, Copy, bytemuck::Pod, bytemuck::Zeroable)]
struct Ping { n: u32 }
impl Message for Ping { const KIND: u16 = 0x201; }

// server: Channel::new(..)?.serve(&mut buf, &mut handler), where the handler does
let ping: Ping = req.decode()?;
req.reply(&Pong { n: ping.n + 1 })?;

// client
let pong: Pong = conn.send(&Ping { n: 41 })?;
```

The API reference is generated by `cargo doc` (see Quick start).

## Demo

The vehicle-signals demo ([demo/README.md](demo/README.md)) runs on the QEMU
QNX 8.0 target from one script. `vsigd` (Rust) answers a safety client (Rust,
priority 40) and an infotainment client (C, priority 10) over native messages
and serves the same signals as `/dev/vehicle/speed` and `/dev/vehicle/brake`.
A watchdog (Rust) gets a heartbeat pulse from each client and restarts one that
stops. The signals are simulated; there is no vehicle bus.

Steps 3 to 9 of a checked run of `tools/demo.sh --headless`, copied from
[docs/demo-log.txt](docs/demo-log.txt) (the signal values and the pid change
from run to run):

```text
== 3. start vsigd: named channel "vehicle" plus two /dev files
vsigd: serving channel "vehicle", /dev/vehicle/speed and /dev/vehicle/brake (own priority 20)

== 4. start the watchdog; it starts both clients
watchdog: started safety-client
watchdog: started infotainment-client
vsigd: hello from safety-client
safety-client: running at priority 40 (SCHED_FIFO), reading brake pressure
vsigd: hello from infotainment-client
infotainment-client: running at priority 10 (SCHED_FIFO), reading speed

== 5. priority inheritance: vsigd (own priority 20) runs each request at its client's priority
vsigd: served safety-client at priority 40
vsigd: served infotainment-client at priority 10

== 6. any program can read the signals as files
# cat /dev/vehicle/speed
speed_kmh=101.2
# cat /dev/vehicle/brake
brake_kpa=666.8

== 7. freeze the infotainment client
# kill -STOP 58613778

== 8. its heartbeats stop; the watchdog restarts it
watchdog: infotainment-client missed 3 heartbeat checks
watchdog: restarting infotainment-client
vsigd: hello from infotainment-client
infotainment-client: running at priority 10 (SCHED_FIFO), reading speed
vsigd: served infotainment-client at priority 10

== 9. stop everything
all demo programs stopped, /dev/vehicle is gone
```

The priorities in the `served` lines are not copied from the request: `vsigd`
asks the kernel (`SchedGet`, `sched_curpriority`) what priority its own thread
runs at while it handles each request. It starts at 20, runs at 40 for the
safety client and at 10 for the infotainment client, and sets no priority
itself. `tools/demo-check.sh` fails if any request is served at another
priority.

## Quick start

You need a Linux x86_64 host (WSL2 works) with:

- **QNX SDP 8.0** in `~/qnx800` (or set `QNX_SDP`), installed with QNX Software
  Center under the free QNX Everywhere non-commercial license, plus QNX's host
  Rust package `com.qnx.qnx800.host.linux.x86_64.rust` (version 0.0.1.00014,
  `rustc 1.85.1-dev`).
- **rustup's cargo of the same version**, since QNX's package has no cargo:
  `rustup toolchain install 1.85.1 --profile minimal` and, for lint,
  `rustup component add rustfmt clippy --toolchain 1.85.1`.
- **QEMU with KVM** (`sudo apt install qemu-system-x86 qemu-utils`, user in the
  `kvm` group) and **clang** for bindgen (`sudo apt install clang libclang-dev`).

[docs/toolchain.md](docs/toolchain.md) has the details and the exact versions
used. Then:

```sh
git clone https://github.com/jakethehoffer/qnx-ipc.git
cd qnx-ipc
source tools/env.sh       # SDP environment, QNX's rustc, target x86_64-pc-nto-qnx800, cargo runner
tools/qemu-up.sh          # builds a QNX 8.0 x86_64 QEMU image once, boots it headless, waits for SSH

cargo run -p qnx-ipc --example ping_pong --target $QNX_RUST_TARGET   # runs on QNX
tools/demo.sh             # the vehicle-signals demo, narrated
tools/test-all.sh         # lint, docs, every test on QNX, demo check; writes docs/test-log.txt

env -u RUSTC cargo doc --no-deps --workspace --target x86_64-unknown-linux-gnu --open   # API docs
tools/qemu-down.sh        # stop the target
```

`cargo run` and `cargo test` for the QNX target copy the binary to the target
over SSH (`root@127.0.0.1`, port 2222) and run it there. To try the 30-second
example, run `cargo run -p qnx-resmgr --example hello_device --target $QNX_RUST_TARGET`
in one terminal and, in another,
`ssh -i ~/.ssh/qnx_target_ed25519 -p 2222 root@127.0.0.1 cat /dev/hello`.

## How it was built

Jake Hoffman, a fourth-year Computer Engineering student at Queen's University,
directed Claude Code, an AI coding agent. Jake chose to enter the hackathon and
approved the design and the plan; the agent wrote the code. Each task was built
test-first against the QEMU QNX target and checked by a separate AI reviewer
before the next one began. [docs/how-it-was-built.md](docs/how-it-was-built.md)
tells the whole story, including the mistakes the agent made and how the
reviewer and the tests on QNX caught them.
